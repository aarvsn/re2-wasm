# CONTRIBUTING

Thanks for your interest in re2-wasm! This document explains how to land
changes in the project. The short version: **open an issue first, keep PRs
small, and run `make check` before pushing.**

## Code of conduct

Be kind. The project is run by volunteers; we treat every contributor with
respect regardless of experience level. Harassment of any kind is not
tolerated and will result in a permanent ban.

## Before you write code

1. **Search the issue tracker.** If nobody has filed an issue for what you
   want to do, file one. We use issues to design the change before code is
   written, which saves everyone time.

2. **Pick something off the roadmap.** The [ROADMAP](ROADMAP.md) lists
   every task we know we need to do. Issues tagged `good-first-issue` are
   specifically picked for new contributors.

3. **Ask if unsure.** Drop a comment on the issue saying you're picking it
   up. We'll confirm no one else is already on it.

## Development setup

```bash
git clone https://github.com/aarvsn/re2-wasm.git
cd re2-wasm
make wasm        # builds web/re2.wasm
make serve       # serves web/ on http://localhost:8080
make test        # runs host unit tests
```

You need Go 1.25+ and a modern browser. See [BUILDING.md](BUILDING.md) for
cross-platform notes.

## Workflow

1. **Branch from `main`.** Use a descriptive name:
   `phase2/bin-cue-parser`, `fix/webgl-context-loss`, etc.

2. **Keep commits focused.** One logical change per commit. If you find
   yourself writing "and also ..." in the commit message, split the PR.

3. **Commit messages.** Use the conventional format:
   ```
   <type>(<scope>): <subject>

   <body explaining why, not what>
   ```
   Types: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `perf`.
   Scope: package name (`engine`, `renderer`, `audio`, ...).

4. **Push and open a PR.** Fill in the PR template; link the issue you're
   closing (`Closes #123`).

## Code quality gate

Every PR must pass `make check`, which runs:

* `go fmt ./...` (format check, no diffs allowed)
* `go vet ./...` on the host
* `GOOS=js GOARCH=wasm go vet ./...` on the WASM target
* `go test -count=1 -race ./...`
* `make wasm` (the binary must build)

Zero warnings, zero errors. The CI workflow runs the same gate on Linux,
Windows, and macOS.

## Code style

* **Idiomatic Go.** Run `gofmt -s` and `go vet` before every commit.
* **Small packages.** If a package grows past ~1000 lines, propose a
  split in an issue first.
* **No dead code.** Every exported symbol must have at least one caller
  (in production code or tests) or be explicitly marked as a public API.
* **No duplicated logic.** If two packages need the same helper, move it
  to a shared package.
* **Document every exported symbol.** Godoc is the API reference; if a
  caller has to read the implementation to understand a function, the doc
  is wrong.

## Tests

* **Table-driven** for input/output mappings (see `engine/clock/clock_test.go`).
* **Sub-tests** (`t.Run`) for variants of the same scenario.
* **Host-only** for everything that doesn't need a browser. The
  `//go:build js && wasm` constraint on js-only files keeps the host test
  suite self-contained.
* **Browser tests** live under `tests/` and run via Playwright (Phase 2+).

## Reviewing

Reviewers focus on:

* Does the change move the roadmap forward?
* Are the tests convincing?
* Is the godoc clear?
* Does the change touch any js-only code? If yes, was the
  `//go:build js && wasm` constraint preserved?
* Are there new dependencies? (We try to keep the dependency tree tiny.)

We aim to review PRs within 3 days. If a PR has been open for a week
without a review, ping the maintainers in the PR thread.
